# Runbook 0.6 — Pipeline rules (manager)

Source: `docs/steps/0.6.md`, decisions D1 (squash only) and D2 (GitHub App token for release-please).
You run everything below yourself; agents never change repo settings. Commands are **PowerShell** on Windows and
need the GitHub CLI logged in as the repo owner (`gh auth status`). Repo: `YoavIsaacs/hiking_app`.
Every self-check is read-only, so the tech lead can run the same commands.

Order matters: do steps 1 and 2 first (settings, App), step 3 (ruleset phase A) before merging the 0.6 PR, and
step 5 (ruleset phase B, adds `pr-title`) only after `pr-title` has reported once on the 0.6 PR (step 4).

## 1. Repo settings: squash merging only

UI: Settings > General > Pull Requests.
- Untick "Allow merge commits" and "Allow rebase merging"; keep "Allow squash merging" ticked.
- "Default commit message" for squash: **Pull request title and description** (the title is the Conventional
  Commit that release-please reads).
- Optional: tick "Automatically delete head branches".

Same thing with the CLI (idempotent):

```powershell
gh api -X PATCH repos/YoavIsaacs/hiking_app `
  -F allow_merge_commit=false -F allow_rebase_merge=false -F allow_squash_merge=true `
  -f squash_merge_commit_title=PR_TITLE -f squash_merge_commit_message=PR_BODY `
  -F delete_branch_on_merge=true
```

Self-check (expected `false`, `true`, `false`, `PR_TITLE`, `PR_BODY`):

```powershell
gh api repos/YoavIsaacs/hiking_app --jq '.allow_merge_commit, .allow_squash_merge, .allow_rebase_merge, .squash_merge_commit_title, .squash_merge_commit_message'
```

## 2. GitHub App for release-please (decision D2)

Why: a release PR opened with the built-in `GITHUB_TOKEN` does not trigger workflows, so the required checks would
never run and the release PR could never merge. `.github/workflows/release-please.yml` mints a short-lived token
from this App instead.

1. Open https://github.com/settings/apps/new (your personal account).
   - GitHub App name: `hike-release-please` (any unique name).
   - Homepage URL: `https://github.com/YoavIsaacs/hiking_app`.
   - Webhook: untick **Active**.
   - Repository permissions: **Contents: Read and write**, **Pull requests: Read and write**,
     **Issues: Read and write** (release-please labels its PRs). Nothing else.
   - Where can this app be installed: **Only on this account**.
   - Create GitHub App.
2. On the App page copy the **Client ID** (starts with `Iv`; not the numeric App ID). Under "Private keys" click
   **Generate a private key**; a `.pem` downloads.
3. Left menu "Install App" > Install on your account > **Only select repositories** > `hiking_app` only.
4. Store the two values (the Client ID is not secret, so it is a variable; the key is a secret). Names are exact:

   ```powershell
   gh variable set RELEASE_APP_CLIENT_ID --repo YoavIsaacs/hiking_app --body "<Client ID>"
   Get-Content -Raw "$HOME\Downloads\<app>.private-key.pem" | gh secret set RELEASE_APP_PRIVATE_KEY --repo YoavIsaacs/hiking_app
   ```
5. Delete the downloaded `.pem` from disk (`Remove-Item "$HOME\Downloads\<app>.private-key.pem"`). Never commit it.
6. "Allow GitHub Actions to create and approve pull requests" (Settings > Actions > General) is **not** needed with
   the App token; leave it off.

Self-check (names only, values are never shown):

```powershell
gh variable list --repo YoavIsaacs/hiking_app   # expect RELEASE_APP_CLIENT_ID
gh secret list --repo YoavIsaacs/hiking_app     # expect RELEASE_APP_PRIVATE_KEY
```

Real-path check (only possible after the 0.6 PR is merged, since the workflow runs on push to `main`):

```powershell
gh run list --repo YoavIsaacs/hiking_app --workflow release-please.yml --limit 1 --json conclusion,headSha --jq '.[0]'
gh pr list --repo YoavIsaacs/hiking_app --label "autorelease: pending" --json number,title,headRefName
gh pr checks <that PR number> --repo YoavIsaacs/hiking_app
```

Expected: latest run `conclusion: success`; one open PR titled `chore(main): release 0.1.0`; `gh pr checks` lists the
CI checks (they ran because the App, not `GITHUB_TOKEN`, opened the PR). If the run fails at "Mint a GitHub App
token", the variable name, the secret, or the App's installation on this repo is wrong. If the PR exists but has
no checks, it was opened with the wrong token.

## 3. Ruleset on `main`, phase A (before merging the 0.6 PR)

Ruleset id 25060155 (active, no bypass actors). Today it has `deletion`, `non_fast_forward` and
`required_status_checks` (lint, api-test, Analyze (python), web-test, e2e, Analyze (javascript-typescript),
api-contract). Phase A adds: pull request required (0 approvals, squash only) and linear history. The bypass list
stays empty, which is what makes the rules apply to admins too.

UI: Settings > Rules > Rulesets > `main`:
- Enforcement status: Active; Bypass list: empty.
- Tick **Restrict deletions**, **Require linear history**, **Block force pushes** (the first and last are on already).
- Tick **Require a pull request before merging**: Required approvals **0**; allowed merge methods **Squash** only;
  leave the other sub-options off.
- Tick **Require status checks to pass**: keep the 7 checks. Leave "Require branches to be up to date" off.
- Save.

Same thing with the CLI. Save this payload as `ruleset-a.json`, then PUT it (PUT replaces the whole ruleset, so
the payload lists every rule):

```json
{
  "name": "main",
  "target": "branch",
  "enforcement": "active",
  "bypass_actors": [],
  "conditions": { "ref_name": { "include": ["~DEFAULT_BRANCH"], "exclude": [] } },
  "rules": [
    { "type": "deletion" },
    { "type": "non_fast_forward" },
    { "type": "required_linear_history" },
    {
      "type": "pull_request",
      "parameters": {
        "required_approving_review_count": 0,
        "dismiss_stale_reviews_on_push": false,
        "require_code_owner_review": false,
        "require_last_push_approval": false,
        "required_review_thread_resolution": false,
        "allowed_merge_methods": ["squash"]
      }
    },
    {
      "type": "required_status_checks",
      "parameters": {
        "strict_required_status_checks_policy": false,
        "do_not_enforce_on_create": false,
        "required_status_checks": [
          { "context": "lint", "integration_id": 15368 },
          { "context": "api-test", "integration_id": 15368 },
          { "context": "web-test", "integration_id": 15368 },
          { "context": "e2e", "integration_id": 15368 },
          { "context": "api-contract", "integration_id": 15368 },
          { "context": "Analyze (python)", "integration_id": 15368 },
          { "context": "Analyze (javascript-typescript)", "integration_id": 15368 }
        ]
      }
    }
  ]
}
```

```powershell
gh api -X PUT repos/YoavIsaacs/hiking_app/rulesets/25060155 --input ruleset-a.json
```

(0 approvals because you are the only maintainer and cannot approve your own PR.)

Self-check (expect the types `deletion`, `non_fast_forward`, `pull_request`, `required_linear_history`,
`required_status_checks`; approvals 0 with `["squash"]`; the 7 contexts; an empty bypass list):

```powershell
gh api repos/YoavIsaacs/hiking_app/rules/branches/main --jq '[.[] | .type] | sort'
gh api repos/YoavIsaacs/hiking_app/rules/branches/main --jq '.[] | select(.type=="pull_request") | .parameters | {required_approving_review_count, allowed_merge_methods}'
gh api repos/YoavIsaacs/hiking_app/rules/branches/main --jq '.[] | select(.type=="required_status_checks") | [.parameters.required_status_checks[].context] | sort'
gh api repos/YoavIsaacs/hiking_app/rulesets/25060155 --jq '{enforcement, bypass_actors}'
```

Real-path check (the tech lead runs it): a direct push from a test commit, `git push origin HEAD:main`, must be
rejected by the ruleset ("Changes must be made through a pull request").


## Why skipped jobs still satisfy the required checks

On a PR, `api-test`, `web-test`, `e2e` and `api-contract` are skipped by a job-level `if:` when their area did not
change. GitHub treats a skipped job as passing for required status checks, so the required list does not change
for it. `lint`, `pr-title` and the two CodeQL jobs always run. Do not add path filters at workflow level
(`on.pull_request.paths`): a workflow that never starts leaves its required check pending forever.

## Nightly and release-please notes

- `nightly.yml` is not a PR check and is not required. It needs no secrets: it uses `GITHUB_TOKEN`, with
  `issues: write` on the failure-reporting job only, and creates the `nightly-failure` label on first use.
- The first release is `v0.1.0`: the manifest starts at `0.0.0` and release-please bumps the minor for a `feat`
  while the version is below 1.0. Merge the release PR when you want to cut the release.
- Close the "Nightly full-suite run failed" issue once the cause is fixed; the next failure opens a new one.
