## Goal
The API runs as a Docker image on Cloud Run (scale to zero) and the web app on Firebase Hosting, both on HTTPS,
deployed from `main` by GitHub Actions authenticating with Workload Identity Federation (no keys); a candidate
revision only gets traffic after its smoke test passes, every PR gets a Firebase preview URL, and the live page
answers in < 5 s cold / < 1 s warm on a phone over mobile data.

## Open decisions (manager)

   this stage: ~$0/month (Cloud Run free tier with min instances 0; Artifact Registry ~$0.10/GB-month for a few
   images). Linking billing moves Firebase to the **Blaze** (pay-as-you-go) plan automatically — Hosting keeps its
   no-cost quota, so still ~$0, but it is no longer a hard-capped free plan; the budget alert is the guard.
   **Recommended:** a new project for this app on your billing account, plus a **budget alert at $5/month**.
   **Decided 2026-10-18 (manager): option A** — keep Cloud Run + Firebase Hosting as built, on a GCP project with a
   card on file; target $0/month (roadmap cost rule). Budget alert at **$1/month** (tightened from $5). Raspberry Pi
   hosting rejected for 0.5; Pis stay a candidate database host in 3.1.
2. **Region.** `me-west1` (Tel Aviv) for Cloud Run and Artifact Registry — closest to you, all three services
   available. Firebase Hosting is a global CDN, so no region applies. **Recommended:** `me-west1`.
   *New since the roadmap change:* Phase 3 adds a database (host decided in 3.1: Neon / Supabase / Pi). If that host
   has no region near Tel Aviv, every API query crosses to it (e.g. Frankfurt), so a European Cloud Run region could be
   faster overall. Moving Cloud Run later = new service URL + rerun of part of the runbook, no code change. Tech lead to
   check the DB hosts' regions before asking.
3. **Names.** GCP project ID (permanent, globally unique). Suggested: `hike-prep-<something>`. The default URLs
   follow it: `https://<service>-<hash>.me-west1.run.app` and `https://<project-id>.web.app`.
   No custom domain in 0.5 (out of scope; can be added later without code changes).
   *New since the roadmap change:* the same Firebase project will hold Firebase Auth (Google sign-in) and real user
   accounts in Phase 3, so the ID names the app, not a stage (no `-dev`/`-test`).
4. **Fake-key check (deferred from 0.1).** Secret scanning and push protection are already **on** (public repo,
   free). Do you want to run the deferred check now — push a known test token to a scratch branch and confirm
   GitHub blocks it? **Recommended:** yes, 2 minutes, done by you from your machine.
5. **New CI-only tool `firebase-tools`** (ADR 0002). Keyless Firebase deploys need the Firebase CLI; the official
   GitHub Action requires a JSON key, which we forbid. Run via `npx firebase-tools@<pinned>` in CI only — not a repo
   dependency. Also new actions `google-github-actions/auth` and `setup-gcloud`. **Recommended:** approve.
6. **Accepted risk (needs your acknowledgement).** A PR from a branch *in this repo* could edit `preview.yml` and

   collaborators join. **Recommended:** accept.
   *New since the roadmap change:* from Phase 3 the project holds user accounts. The preview SA has Hosting roles only

7. **Phone-timing pass rule.** Roadmap: "< 5 s cold and < 1 s warm" without saying every run or median.

## Checkpoint
**Checkpoint:** both live on HTTPS; on your phone over mobile data the page shows the API response in < 5 s cold and < 1 s warm; a deliberately broken deploy rolls back with no manual step

How it will be measured:
- `curl -sI https://<api>/health` and `https://<project>.web.app` → 200 over HTTPS; `/health` `git_sha` == `main` HEAD.
- Phone (manager): mobile data, Wi-Fi off. Cold = after ≥ 15 min idle (Cloud Run scaled to 0; confirm 0 instances
  in the console or by revision metrics), load the page, time until version text shows; warm = reload within 1 min.
  3 runs each, record all numbers. Procedure written by qa.
- Broken deploy: a commit to `main` whose image starts but `/health` returns a wrong `git_sha` (or 500) →
  `deploy-api` fails at smoke, traffic stays on the previous revision (`gcloud run services describe` shown in the
  workflow log, or the live `/health` still returns the old SHA). Run link recorded. Then fix-forward.

## Phone timing procedure (QA, for the manager)
**Setup.** Wi-Fi off, mobile data on. Normal browser tab (not an installed PWA), other tabs closed. Have
`https://<PROJECT_ID>.web.app` and a stopwatch. Clear site data first (Chrome: Settings → Privacy → Delete browsing
data → cached images and files; Safari: Settings → Safari → Clear History and Website Data).

**Cold (before each cold run).** ≥ 15 min with no API requests (no page, no curl, no CI deploy). Confirm 0 instances:
Cloud Console → Cloud Run → `hike-api` → Metrics → "Container instance count" reads 0. If not, wait 15 min more.

**Timing.** Start when you tap Go on the URL in a fresh tab; stop when the "Version" row shows a real version string
(not the page frame or a "checking" state). Round to 0.1 s.

**Runs.** 3 cold (each with its own idle wait + instance check, clear site data after each); 3 warm right after a cold
run, within 1 min, by reload, cache not cleared.

| Run | Type | Idle (min) / 0 instances confirmed | Seconds to version text | Pass |
| --- | --- | --- | --- | --- |
| 1 | cold | | | |
| 2 | cold | | | |
| 3 | cold | | | |
| 4 | warm | n/a | | |
| 5 | warm | n/a | | |
| 6 | warm | n/a | | |

Also record: date/time, phone model, carrier and signal, browser, `git_sha` from `/health`. Pass rule: Open decision 7.
On a fail: report the numbers; don't change min instances (costs money) without a decision.
